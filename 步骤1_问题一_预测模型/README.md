# 步骤 1：问题一短期 GPU 需求预测

本目录实现问题一中调度前的 24 小时 GPU 需求预测。预测输出是后续调度模型的输入，不替代任务分配、开工或算电协同优化决策。

当前版本以来源区域 × 任务类型 × 小时为预测单元，直接预测该单元的总 GPU 需求；通过完整历史小时“任务包”Bootstrap 给出不确定性区间。完整模型理由、参数选择、回测和测试结果见 [问题一_预测模型完整报告.md](./问题一_预测模型完整报告.md)。

## 目录与依赖关系

```text

├─ 基础调度结果/                             # 任务分配、约束检查与甘特图
├─ 步骤1_问题一_预测模型_记忆.md             # 实施过程、结果口径与后续使用边界
└─ 问题一_预测模型完整报告.md                 # 可直接阅读的完整报告
```

上游输入固定为：

```text
../步骤0_数据预处理与分析/processed/fact_tasks.csv
```

因此，首次运行或步骤 0 数据口径变更后，必须先执行步骤 0 的 `run_pipeline.py`。

## 运行方法

在本目录执行：

```powershell
python -m pip install pandas numpy matplotlib
python run_forecast.py
```

脚本按 `forecast_config.json` 中的固定随机种子和配置运行，并会重建 `预测结果/`。若要对比不同设定，应复制保存原结果，修改配置后重新运行，并在报告中记录变更原因；不要利用测试窗真实值反向选择参数。

## 模型口径

### 预测对象

令来源区域为 `r`、任务类型为 `k`、小时为 `t`，预测目标是

```text
D(r, k, t) = 该小时在来源区域 r 到达、任务类型为 k 的全部任务 GPU_Demand 之和
```

共有 6 个来源区域和 3 个任务类型，即 18 条小时序列。该设计同时保留任务所属区域和类别，避免先拆成“任务数模型”和“单任务 GPU 需求模型”后再引入独立性假设。

### 训练、验证与测试边界

| 用途 | 小时索引 |
| --- | --- |
| 候选模型训练 | 0–2351 |
| 验证与模型选择 | 2352–2375 |
| 最终训练 | 0–2375 |
| 固定的 24 小时测试窗 | 2376–2399 |

每次均从预测原点一次性预测未来 24 小时。预测期内的真实任务不能进入滚动均值、滞后变量、参数估计或模型选择；这保证评估的是调度前可获得信息下的离线预测能力。

### 候选点预测模型

脚本比较以下模型，并以验证集 WAPE 为主、MAE 为辅选择点预测模型：

- `direct_mean`：使用训练期同一来源区域 × 任务类型序列的全历史均值；当前最终选中模型。
- `rolling_24`、`rolling_168`、`rolling_336`：分别使用最近 24、168、336 小时均值。
- `seasonal_daily`、`seasonal_weekly`：按日/周对应时段的历史模式预测。

除单次验证外，脚本还使用 48 个、间隔 24 小时的滚动预测原点检验稳定性。具体模型表现、选择理由和参数比较均在完整报告中列出。

### 区间预测

对预测原点之前的完整历史小时任务包进行 10,000 次 Bootstrap 抽样。每个抽样单位保留同一小时内全部任务的任务数、GPU 需求、时长和 SLA 等联合结构，再汇总为 18 个预测单元及区域/系统层级。

区间分位点并非直接套用名义分位数，而是依据训练期滚动回测进行分层经验校准：

| 输出层级 | 80% 区间 | 95% 区间 |
| --- | --- | --- |
| 来源区域 × 任务类型 | P17–P83 | P5–P95 |
| 区域汇总、系统汇总 | P9.5–P90.5 | P3–P97 |

所有数值可在 `forecast_config.json` 和 `预测结果/forecast_interval_config.csv` 中核验。

## 后续调度模型如何使用

- 点预测可作为每个来源区域、任务类型、小时的基准到达 GPU 需求。
- 预测区间或 Bootstrap 情景可用于鲁棒/随机调度，而不能把区间上下界误认为确定性任务量。
- 具体任务的目标执行区域、整数开工、跨小时计算重叠、网络时延和电力约束，属于后续调度模型的决策与约束；它们不应在预测阶段被提前“优化”。

## 问题一末 24 小时基础调度

预测评价与基础调度使用不同输入：前者预测需求，后者必须使用 `2376–2399` 的实际到达任务。`run_basic_schedule.py` 额外纳入在 `t=2376` 仍可能执行的前序任务作为边界占用，并把结算期延伸至 `t=2405`。

脚本的硬约束为单向网络时延、实时任务到达即启动、任务完成期限、区域 GPU 容量、IT 功率和设施功率；IT/设施功率均叠加逐时 `NonAI_IT_Load_MW`。负荷按 `task_hour_profile.csv` 的分钟级跨小时重叠精确计算。

当前数据中所有任务到达即启动可行，因此脚本固定开工时刻，仅在时延可行区域中最小化最大 GPU 利用率。网络时延作为 SLA 硬约束和结果评价指标，不再进行独立的时延平局打破。若迁移至其他数据后即时开工不可行，应恢复 Batch/Training 的延后开工建模。默认单次 MIP 求解最长 1,800 秒，并输出真实 MIP gap。

运行：

```powershell
python run_basic_schedule.py
```

主要输出位于 `基础调度结果/`：

- `task_schedule.csv`：任务执行区域、开工/结束时刻、等待与时延；
- `region_hour_schedule.csv`：区域逐时 GPU、IT 和设施负荷；
- `constraint_checks.csv`：逐项硬约束检查；
- `q1_schedule_report.md` 与 `figures/`：调度汇总、甘特图和 GPU 利用率图。
- [问题一_基础调度完整报告.md](./问题一_基础调度完整报告.md)：统一的模型、约束、实施与结果说明。
