# 问题一：末 24 小时基础调度模型完整报告

> 本文统一记录华数杯 C 题问题一的基础调度模型、实现口径、约束与当前运行结果。预测模型与基础调度相互独立：预测部分用于短期需求评价；本调度部分严格使用 `2376–2399` 小时的实际到达任务。

## 1. 调度范围与数据口径

### 1.1 调度任务集

- **主任务**：到达小时属于 `2376–2399` 的 538 个实际任务；其中 AITraining 194 个、BatchInference 184 个、RealTimeInference 160 个。
- **边界携入任务**：到达早于 2376、按即时执行会在 2376 后仍有资源占用的 58 个任务。它们用于构造末窗开始时的资源占用背景，不计入主任务绩效统计。
- **结算期**：模型计算 `2376–2405` 的资源使用；所有任务必须在第 2406 小时前结束，不能占用 `t=2406`。

### 1.2 固定即时开工口径

本数据中，所有主任务均可在到达时刻启动并满足 GPU、IT 功率、设施功率、网络时延和完成期限。故本版本固定：

\[
s_i=ArrivalHour_i
\]

即不再将 BatchInference、AITraining 的延后开工时间作为决策变量。这样既符合问题一“基础调度”的简明定位，也避免无必要地扩大整数规划规模。若后续数据中即时开工不可行，应恢复可延后任务的开工时刻决策。

### 1.3 使用的数据表

| 数据表 | 使用方式 |
| --- | --- |
| `fact_tasks.csv` | 任务类型、到达时刻、GPU 需求、时长、SLA 与完成期限。 |
| `task_hour_profile.csv` | 任务分钟级时长对应的跨小时实际重叠量。 |
| `task_region_eligibility.csv` | 单向网络时延与可行执行区域筛选。 |
| `dim_region.csv` | GPU 容量、IT 功率、PUE 与设施功率上限。 |
| `fact_region_hour_input.csv` | 逐时不可迁移 `NonAI_IT_Load_MW`。 |

## 2. 模型建立

### 2.1 集合、参数与变量

令任务集合为 \(I\)，区域集合为 \(R\)，小时集合为 \(T=\{2376,\ldots,2405\}\)。对任务 \(i\)：

- \(g_i\)：GPU 需求；
- \(p_i\)：任务类型对应单等效 GPU 的 IT 功率；
- \(a_{it}\)：任务在小时 \(t\) 内的实际重叠时长；
- \(\mathcal R_i\)：网络时延满足 SLA 的可行执行区域集合；
- \(N_{rt}\)：区域逐时非 AI IT 负荷；
- \(C_r^{GPU},C_r^{IT},C_r^{Facility},PUE_r\)：区域 GPU、IT、设施容量和 PUE。

决策变量：

\[
x_{ir}=\begin{cases}
1,&\text{任务 }i\text{ 在区域 }r\text{ 执行}\\
0,&\text{否则}
\end{cases}
\]

\[
U^{max}\ge0
\]

其中 \(U^{max}\) 为任一“区域—小时”的最大 GPU 利用率。

### 2.2 负荷映射

任务的逐时 GPU 占用和 AI IT 负荷分别为：

\[
GPUUsed_{rt}=\sum_{i\in I}g_i a_{it}x_{ir}
\]

\[
AIIT_{rt}=\sum_{i\in I}g_i p_i a_{it}x_{ir}
\]

\[
IT_{rt}=N_{rt}+AIIT_{rt},\qquad Facility_{rt}=PUE_r\cdot IT_{rt}
\]

这里的 \(a_{it}\) 直接取自任务—小时剖面，因此跨小时任务不会被整小时截断。例如一项持续 3.3 小时的任务，在首、尾小时按实际重叠比例占用 GPU 和功率。

### 2.3 目标函数

在所有任务即时开工且网络 SLA 满足的前提下，最小化最大 GPU 利用率：

\[
\min U^{max}
\]

该目标将可迁移任务分配至不同区域，使最繁忙区域的 GPU 资源压力最低。网络时延不再作为额外优化目标，而是硬约束及最终评价指标。

### 2.4 约束条件

**任务唯一分配**

\[
\sum_{r\in\mathcal R_i}x_{ir}=1,\qquad\forall i\in I
\]

**网络时延与实时 SLA**

候选执行区域仅保留 \(r\in\mathcal R_i\)，故自动满足：

\[
Latency(SourceRegion_i,r)\le MaxLatency_i
\]

所有实时推理任务固定 \(s_i=ArrivalHour_i\)，其他任务在当前模型中也采取同一即时开工口径。

**GPU 容量**

\[
GPUUsed_{rt}\le C_r^{GPU},\qquad\forall r,t
\]

**IT 功率容量**

\[
N_{rt}+AIIT_{rt}\le C_r^{IT},\qquad\forall r,t
\]

**设施功率容量**

\[
PUE_r(N_{rt}+AIIT_{rt})\le C_r^{Facility},\qquad\forall r,t
\]

**峰值利用率定义**

\[
\frac{GPUUsed_{rt}}{C_r^{GPU}}\le U^{max},\qquad\forall r,t
\]

**完成期限**

即时开工后的结束边界必须满足任务的 `LatestFinishHour`，且严格小于等于 2406；第 2406 小时不允许有任何任务运行。

## 3. 实施步骤

1. 从步骤 0 的标准化表读取任务、时延、功率映射、区域资源与非 AI 负荷。
2. 筛选 538 个主任务和 58 个携入任务，并固定每项任务开工时刻为到达时刻。
3. 按每项任务的单向时延阈值生成“任务 × 可行执行区域”候选列；当前共生成 2,936 个二元变量。
4. 将任务分钟级重叠剖面映射至 `2376–2405` 的区域—小时容量约束；共形成 180 个区域—小时资源单元。
5. 使用 SciPy `milp` 调用 HiGHS 求解单阶段最小峰值 GPU 利用率模型。当前配置为相对 gap `1e-4`、最多 1,800 秒。
6. 输出任务分配、区域逐时负荷、硬约束检查、任务类型去向汇总、甘特图和区域 GPU 利用率图。

运行命令：

```powershell
cd '步骤1_问题一_预测模型'
python run_basic_schedule.py
```

## 4. 当前长时运行结果

本次结果由原单阶段峰值均衡子问题产生；其数学模型与本报告的统一模型相同。

| 指标 | 结果 |
| --- | ---: |
| 主任务 / 携入任务 | 538 / 58 |
| 最大 GPU 利用率 | **56.1832%** |
| 峰值 MIP 相对 gap | **0.020589%** |
| 主任务迁移数 / 迁移率 | 393 / 73.05% |
| 主任务平均等待时间 | 0 h |
| 主任务平均网络时延 | 29.7881 ms |
| 来源区立即执行参考方案峰值 | 108.5128%（不可行） |

求解器在 1,800 秒限制内给出高质量近优解，尚未以 `1e-4` gap 停止。因此可表述为“峰值利用率高质量近优解”，不能表述为已证明的严格全局最优。按当前 gap 推算，最大 GPU 利用率距已知下界约不超过 0.012 个百分点。

### 4.1 硬约束检查

所有 596 个任务均通过检查：任务唯一分配、实时即时启动、网络时延、完成期限、结算边界与分钟级时长守恒均通过。逐区域逐小时资源约束同样全部可行：

| 约束 | 最大违例 | 结论 |
| --- | ---: | --- |
| GPU 容量 | -236.6667 GPU | 通过，仍有 GPU 余量。 |
| IT 功率 | -0.006667 MW | 通过，但 RegionA/B/C 个别时段接近上限。 |
| 设施功率 | -0.009000 MW | 通过，但与 IT 功率约束一致地接近上限。 |

负值代表“实际值减上限”，因此均为可行。结果说明：问题一的关键瓶颈不是 GPU 总量，而是东部区域叠加非 AI 负荷后的 IT 与设施功率空间。这是后续问题二至四进一步开展算电协同优化的重要依据。
